چند پروژه پیش‌تر بخش‌هایی از این مسئله را هدف گرفته‌اند. پیش از ساختن هر چیزی، **کد** هر کدام را خواندیم، نه فقط README آن را، و آنچه واقعاً انجام می‌دهد را بر [نُه لایهٔ](/persian-cli/fa/problem-map/) خودمان نگاشتیم.

:::note[چگونه بررسی شد]
فهرست اولیه از یک گفت‌وگو با مدل زبانی آمده بود؛ پس هیچ‌چیزش را بی‌بررسی نپذیرفتیم. وجود هر پروژه تأیید شد، کدش فقط برای خواندن کپی شد (هیچ‌چیز ساخته یا اجرا نشد) و در یک کامیت مشخص خوانده شد. یادداشت هر پروژه به مسیر فایل و شمارهٔ خط ارجاع می‌دهد و آنچه **در کد تأیید شده** را از آنچه **فقط در README ادعا شده** جدا نگه می‌دارد.
:::

## پایه‌ها و پیشینه

- **مسئلهٔ [#553](https://github.com/neovim/neovim/issues/553) در Neovim، «پشتیبانی از زبان‌های دوجهتی»**: از سال ۲۰۱۴ باز است و ۴۷ نظر دارد. این مسئله بیش از یک دهه قدمت دارد.
- **[BiDi in Terminal Emulators](https://terminal-wg.pages.freedesktop.org/bidi/)** (اگمونت کوبلینگر، ۲۰۱۹): پیش‌نویس استانداردی برای اینکه دوجهتی کار ترمینال است یا برنامه. VTE آن را پیاده کرده؛ هیچ‌یک از این ده پروژه از آن استفاده نمی‌کند.
- **موتورها:** [HarfBuzz](https://harfbuzz.github.io/) برای شکل‌دهی؛ [FriBidi](https://github.com/fribidi/fribidi) و [ICU](https://icu.unicode.org/) برای UAX #9. هر پروژه‌ای که شکل‌دهی را درست انجام داد، آن را به موتوری از همین دست سپرد.
