# Split RTL ownership; never shim it

No Rust helper, plugin or shim can correctly fix Persian/Arabic rendering for *every* terminal app. That isn't a gap in tooling. It follows from how terminals work: UAX #9 has to run on a whole logical paragraph, and only the application knows the paragraph, while only the renderer knows the font, the window width and the soft wraps. The one design document in this space, Egmont Koblinger's freedesktop "BiDi in Terminal Emulators" draft, therefore splits responsibility. The terminal handles BiDi-unaware programs (implicit mode, the default) and the app handles BiDi-aware ones (explicit mode, which it requests with `CSI 8 l`). Responsibility for any given paragraph must sit in exactly one place ([Why terminals are special](https://terminal-wg.pages.freedesktop.org/bidi/bidi-intro/why-terminals-are-special.html)). The best architecture for persian-cli is one Rust core crate, a cell-grid BiDi layout engine (call it `bidi-grid`), shipped through three front-ends: an ANSI-aware `rtl` pipe filter now; a virtual-screen PTY proxy that runs inside a Zellij pane, turns itself off on the alternate screen and honours BDSM; and a ratatui adapter for apps you own. Upstream work on WezTerm and Zellij reuses the same crate. Two routes should be dropped. The DYLD/LD_PRELOAD shim is dead on macOS, because Claude Code's binary is hardened and simply ignores injection. A Zellij WASM plugin can't rewrite another pane's output. The WezTerm + Zellij combination adds two blockers that decide the plan: Zellij currently drops Arabic harakat (diacritics) before any BiDi pass could see them, and WezTerm discards the isolate characters that tmux uses to keep RTL text from leaking across pane borders.

## A layer outside the app sees cropped fragments, so "universal" is unsound

Koblinger states the core problem plainly: "Cropping the in-memory string and then applying the BiDi algorithm produces faulty visual layout… The BiDi algorithm cannot be run on partial data, it must be run on the entire paragraph, and hence can only be run by someone who is aware of the entire paragraph. The only such component is the application." Shaping has the same dependency on neighbouring characters ([Why terminals are special](https://terminal-wg.pages.freedesktop.org/bidi/bidi-intro/why-terminals-are-special.html)). A full-screen TUI such as vim, htop, lazygit or Claude Code's Ink UI positions its cells absolutely. Anything downstream of it, whether a PTY proxy, a multiplexer or a shim, receives fragments of a layout the app has already cropped, and the stream carries no marker of where one UI field ends and the next begins. htop's `9PullDn10Quit` is a single "word" of unrelated widgets, told apart only by colour attributes. Line-oriented tools such as `cat` and `git log` send whole logical paragraphs, but **the byte stream alone can't tell those two cases apart**.

The second failure mode is **double ownership**. Emacs already does its own BiDi, so a BiDi-aware terminal reverses its output a second time, back into the wrong order. Vim and Neovim don't do BiDi but do shape Arabic on the reversed (LTR) order ([Terminal-WG: Applications](https://terminal-wg.pages.freedesktop.org/bidi/prior-work/applications.html)). In WezTerm this shows up directly: Neovim's `arabicshape` emits Presentation Forms-B and relies on them for lam-alef, while WezTerm also shapes, so the user has to pick one owner and loses something either way ([wezterm#784](https://github.com/wezterm/wezterm/issues/784)). The spec's answer is negotiation, not cleverness. **Implicit** (`CSI 8 h`, the default) means the terminal does UAX #9 and shaping. **Explicit** (`CSI 8 l`) means the app sends visual order and the terminal leaves it alone. SCP (`CSI 1/2/0 SP k`) sets the paragraph direction ([escape sequences](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/escape-sequences.html)). Every component persian-cli builds has to speak this protocol: honour `CSI 8 l` from the child, and never reorder an explicit paragraph.

The standards landscape is thin and stale. The draft is still v0.1 from 2019-01-29 ([About](https://terminal-wg.pages.freedesktop.org/bidi/about.html)). All 10 issues on its tracker date from 2019 and remain open, including "Rework shaping" and "Arabic joining" ([GitLab issues](https://gitlab.freedesktop.org/api/v4/projects/terminal-wg%2Fbidi/issues?state=all)). VTE is the full reference implementation, mintty implements the sequences as "experimental" ([mintty CtrlSeqs](https://github.com/mintty/mintty/wiki/CtrlSeqs)), and WezTerm implements BDSM and SCP but treats each physical line as its own paragraph ([terminalstate/mod.rs](https://raw.githubusercontent.com/wezterm/wezterm/main/term/src/terminalstate/mod.rs)). Microsoft's Windows Terminal team sums up where things stand: RTL "requires cooperation from both the terminal emulator and the commandline application… there's not a standard" ([terminal#20302](https://github.com/microsoft/terminal/issues/20302)). No formal impossibility proof exists. This is a reasoned position, but every implementer who has tried has run into it.

## Persian shaping and cell width break any layer that emits characters

Arabic script joins cursively. Dual-joining letters have four contextual forms. ZWNJ (U+200C), which Persian uses constantly in forms like می‌ and the plural ـها, blocks the join without taking any width. **Lam-alef is an obligatory ligature that fuses two code points into one glyph**, and that collides with a grid of two cells ([Unicode Core Spec ch. 9](https://www.unicode.org/versions/Unicode18.0.0/core-spec/chapter-9/)). Each existing terminal takes a different side. mintty defaults to two cells with a gap and offers `CSI ? 2521 h` for one cell ([mintty CtrlSeqs](https://github.com/mintty/mintty/wiki/CtrlSeqs)). VTE turns the ligature off entirely and shapes with FriBidi presentation forms, not HarfBuzz ([VTE bidi.cc](https://raw.githubusercontent.com/GNOME/vte/master/src/bidi.cc)). WezTerm leaves a stray extra cell after "السلام" ([wezterm#6791](https://github.com/wezterm/wezterm/issues/6791)). UAX #9 itself says that where shaping is involved, "the width calculations must be based on the shaped glyphs" ([UAX #9](https://www.unicode.org/reports/tr9/)). The project's own catalog found the width layer "unsolved everywhere" ([prior-art.md](https://github.com/mbaneshi/persian-cli/blob/dev/docs/research/prior-art.md)).

This creates a dilemma for anything other than a renderer. A proxy or filter emits *code points*, not glyphs, so `harfrust` (the official HarfBuzz Rust port, v0.14.0, Oct 2026) is no use inside one ([crates.io harfrust](https://crates.io/crates/harfrust)). That leaves two options. The layer can emit base letters in visual order and hope the host shapes them correctly. That's risky: a shaper that receives a run of Arabic in LTR visual order will probably join it backwards, with initial and final forms swapped, and nobody has tested this on WezTerm yet. Or the layer can substitute presentation forms, which don't depend on join state. That's the route bicon, estaterm and fribidi take, and **it permanently corrupts the text**: copy yields U+FBxx/FExx code points and search fails. Unicode says presentation forms "should not be used in general interchange" ([Core Spec ch. 9](https://www.unicode.org/versions/Unicode18.0.0/core-spec/chapter-9/)). **No layer outside the renderer can deliver both correct joining and logical text in the host's buffer.** The real fix for shaping lives in the emulator.

A few Persian-specific rules have to be built into the core crate. Persian digits ۰–۹ (U+06F0–06F9) have bidi class **EN**, while Arabic-Indic digits (U+0660–0669) are **AN**, and rule W2 converts EN to AN after an AL character, so dates like `۱۴۰۵/۰۷/۱۹` need tests with both digit sets ([UAX #9](https://www.unicode.org/reports/tr9/)). `unicode-bidi` skips rules L3 and L4 ("This does not apply [Rule L3] or [Rule L4] around combining characters or mirroring"). The caller therefore has to reverse by grapheme cluster, so harakat stay attached to their base letter, and mirror brackets with `unicode-bidi-mirroring` ([servo/unicode-bidi](https://github.com/servo/unicode-bidi/blob/main/src/lib.rs)). For presentation-form output, `ar-reshaper` (no-std, MIT) carries the real Persian forms for ی and ک. Reading its code shows ZWNJ correctly breaks joining, but only by falling through an "unsupported letter" branch, not by deliberate handling ([ar-reshaper](https://github.com/YouKnow-sys/ar-reshaper)). Ligatures should default to off for terminals, because many terminal fonts don't have the glyphs ([pub.dev arabic_bidi](https://pub.dev/packages/arabic_bidi)).

## Six candidate architectures, ranked by what they can actually reach

| Route | Reaches "any app"? | Shaping | Copy/search | Verdict |
|---|---|---|---|---|
| Emulator-native (WezTerm patch/PR) | Yes for implicit, line-oriented output; TUIs via BDSM | Correct (HarfBuzz per run) | Logical (model stays logical) | Correct long-term home; upstream-dependent |
| Virtual-screen PTY proxy | Main-screen output, prompts, LLM CLIs; not alt-screen TUIs | Presentation forms or host-dependent | Visual in host | Best portable "any app" vehicle today |
| Zellij core patch | Same as proxy, per pane | Same as proxy | Logical (Zellij owns selection) | Best multiplexer home; blocked on combining marks |
| ratatui / TUI-library adapter | Only apps that adopt it | App-chosen | App-owned | Ecosystem value, not "any app" |
| Pipe filter (`cmd \| rtl`) | Non-interactive output only | Presentation forms | Visual | Cheap, ships first, doubles as test harness |
| Zellij WASM plugin | No (mirror-pane demo only) | n/a | n/a | Reject |
| DYLD / LD_PRELOAD shim | No | Presentation forms | Visual | Reject |

### The shim is dead on macOS

Apple documents that dyld ignores `DYLD_INSERT_LIBRARIES` for SIP-protected and hardened-runtime executables ([Apple Developer Forums 731358](https://developer.apple.com/forums/thread/731358)). In hands-on tests during this research, a `write()` interposer recorded **zero hooked writes** from `/bin/echo` and from the user's `~/.local/bin/claude`, which is code-signed with the hardened `runtime` flag. It did hook ad-hoc-signed Homebrew `node` and `lazygit`. Even where injection worked, writes made through stdio inside libSystem (`printf`) never passed through the interposed `write()`. Beyond these macOS specifics, a shim has the structural flaws of a stream transformer: a single `write()` can end in the middle of an escape sequence, the shim has no model of the screen, and it can't follow `exec` into protected binaries, `sudo` or `ssh`. Koblinger floated LD_PRELOAD only for the narrow case of mirroring ncurses box-drawing borders ([Miscellaneous](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/misc.html)).

### A Zellij plugin can read panes but not rewrite them

The Zellij plugin API can read another pane's contents through `PaneRenderReport`, which arrives ANSI-stripped and is "fired periodically". Plugins can also write to a pane's stdin, hide panes and intercept keys, but **no event or command transforms another pane's output** ([zellij plugin events](https://zellij.dev/documentation/plugin-api-events); [PaneContents](https://docs.rs/zellij-tile/latest/zellij_tile/prelude/struct.PaneContents.html)). The only plugin design that works is a "mirror pane": hide the real pane and render a BiDi copy of it. That copy loses colours, lags behind the real pane, and needs its own mouse handling, so it's a read-only preview at best.

### The proxy works only with a full screen model, and bicon proves why

bicon, the canonical PTY wrapper and a project of more than a decade (2013+), is a **stream transformer with no screen model**. It treats any run between control characters as a paragraph, converts it to presentation forms with FriBidi, and patches earlier output with backspaces ("We can't handle long paragraphs :-(") ([bicon_read.c](https://github.com/behdad/bicon/blob/master/bicon/bicon_read.c)). (This corrects the project's estaterm note, which implied bicon had a screen model.) Its maintainer calls its copy-order bug "inherent to this approach" and, on the erase bug, recommends "terminals that have native support for bidi" ([bicon #11](https://github.com/behdad/bicon/issues/11); [bicon #18](https://github.com/behdad/bicon/issues/18)). A credible Rust proxy has to differ in exactly one way: **a full VT emulator is the source of truth, and visual frames are rendered from it by diffing**. **tattoy** already demonstrates that pipeline in Rust, without any BiDi: a shadow PTY (`portable-pty`) feeds a headless `wezterm_term::Terminal`, layers are composited on a `termwiz` Surface, and a diff goes out to the real terminal ([tattoy](https://github.com/tattoy-org/tattoy)). A search found no Rust BiDi proxy on crates.io ([crates.io search](https://crates.io/search?q=bidi%20terminal)).

With a screen model in place, the proxy can handle most of the hard problems. Cursor-addressed redraws, readline erase and `\r` progress bars become ordinary grid updates, which fixes exactly the bicon bugs (#18, and zsh-syntax-highlighting in #24). Each frame, the proxy computes the row's `reorder_visual` permutation, places the host cursor at the visual position of the logical cursor, swallows `CSI 6n` and answers it with logical coordinates, and maps incoming SGR mouse reports from visual to logical columns. It also knows which lines are soft-wrapped, so it can resolve BiDi levels over the whole wrapped paragraph and reorder row by row, as UAX #9 intends. Cursor placement at the boundary between an LTR and an RTL run stays inherently ambiguous: the algorithm "doesn't provide a mapping for the boundaries between" characters ([The cursed cursor](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/cursor.html)). Copy from the host terminal also stays in visual order. The proxy can't touch alternate-screen TUIs, which own their own layout. The project catalog records that every stream transformer "gives up on full-screen apps" ([prior-art.md](https://github.com/mbaneshi/persian-cli/blob/dev/docs/research/prior-art.md)). That isn't a failure: it's explicit-mode "damage control" as the spec intends.

## WezTerm and Zellij each carry one blocking defect

WezTerm is the only mainstream Rust emulator with UAX #9 wired end to end. It has opt-in `bidi_enabled`, BDSM and SCP handling, and HarfBuzz shaping per run in the resolved direction. Its changelog still calls the feature "Experimental (and incomplete!)" ([wezterm changelog](https://github.com/wezterm/wezterm/blob/main/docs/changelog.md)). The gaps are known: the paragraph is the physical line, the cursor doesn't flip when editing inside RTL runs ([#784](https://github.com/wezterm/wezterm/issues/784)), lam-alef width is wrong ([#6791](https://github.com/wezterm/wezterm/issues/6791)), and **BiDi controls such as FSI (U+2068) are dropped from the model** and lost on copy ([performer.rs](https://raw.githubusercontent.com/wezterm/wezterm/main/term/src/terminalstate/performer.rs)). No glyph or render hook is exposed to Lua, so any change means a PR or a fork ([wezterm Lua module](https://wezterm.org/config/lua/wezterm/)). The last tagged release is still 20240203, even though `main` is active as of October 2026, so patches reach users only through nightlies ([wezterm commits](https://github.com/wezterm/wezterm/commits/main)).

The dropped controls matter more than they first appear to, because of Zellij. When a host terminal does BiDi, RTL runs in one pane leak across the split border into the next. tmux fixed this only by wrapping each pane's content in directional isolates, and its maintainer added that BiDi "should be the responsibility of applications" ([tmux #2425](https://github.com/tmux/tmux/issues/2425)). **WezTerm discards those isolates.** So turning on WezTerm's per-line BiDi underneath Zellij makes it treat a row containing several panes as one paragraph, and the tmux-style containment can't work. That's an inference from the two facts above, and the first Phase 0 test should confirm it. The second blocker sits in Zellij: it **drops every zero-width combining mark**, Arabic harakat included. The issue has been open since 2022, and the fix PR #5500 is still unmerged. A September 2026 comment reports that Zellij 0.45.1 "preserved 0 of 4 nonspacing marks, while tmux preserved all 4" ([zellij #1538](https://github.com/zellij-org/zellij/issues/1538); [PR #5500](https://github.com/zellij-org/zellij/pull/5500); [#4447](https://github.com/zellij-org/zellij/issues/4447)). A search found no BiDi or RTL issue in Zellij at all. Inside this stack, then, Persian text with diacritics is damaged before any layer of ours ever sees it.

Even so, Zellij core is the best long-term host outside the emulator. A multiplexer has the full grid, the scrollback and the pane boundaries, so each pane is naturally its own paragraph set, which removes the leakage problem. Zellij also owns selection, so its copy can stay logical, which a dumb proxy can't offer. It inherits the same shaping dilemma when it emits to WezTerm, though, and maintainers have shown no appetite for the feature.

## The recommended Rust path for persian-cli

**Phase 0, measure first (days).** Build a Persian test corpus: ZWNJ words, both digit sets, lam-alef, harakat, mixed paths and code, brackets. Run it against WezTerm with `bidi_enabled` on and off, both outside and inside Zellij. Measure four things: pane-border leakage, ZWNJ survival (WezTerm's zero-width filtering could drop it), how WezTerm's shaper handles Arabic sent in visual order with BiDi off, and what `unicode-width` 0.2.2 returns for U+200C and harakat. Use `fribidi --nobreak --nopad` as the baseline. In earlier testing it reordered and shaped a mixed Persian/Latin/digit sentence correctly, but its own line breaking split می‌خواهم in the middle of the word ([fribidi(1)](https://unix.com/man-page/linux/1/fribidi/)). The visual-order shaping result decides whether the proxy can emit logical code points or has to fall back to presentation forms.

**Phase 1, build `bidi-grid` (the core crate).** The input is a row of logical cells (or a soft-wrapped paragraph of them), each with its grapheme, width and attributes, plus the BDSM mode, the SCP direction hint and an optional pane boundary. The output is visual runs, `log2vis` and `vis2log` permutations over cells, the cursor's visual x with a direction flag, a mapping from selection to logical ranges, a width policy for lam-alef, and a zero-cost fast path for rows with no strong RTL characters. That fast path matters because kitty's maintainer rejected any "significant negative performance impact on normal (i.e. no bidi) usage" ([kitty#2109](https://github.com/kovidgoyal/kitty/issues/2109)). The stack is `unicode-segmentation`, then `unicode-bidi` or `wezterm-bidi` (both pass the full BidiTest and BidiCharacterTest suites; [wezterm-bidi](https://github.com/wezterm/wezterm/tree/main/bidi)), then `unicode-bidi-mirroring`, an optional `ar-reshaper` with ligatures off, and `unicode-width`. Shaping goes behind an adapter trait so that a renderer can plug in `harfrust`. **No such crate exists.** WezTerm, Ghostty's PR #11079, the cosmic-term patch and termenal-web each rebuilt this middle layer by hand, and Ghostty's maintainers had to ask two contributors with divergent designs to "come up with a unified approach" ([ghostty#1442](https://github.com/ghostty-org/ghostty/issues/1442)). That makes it the highest-leverage piece of work in the plan.

**Phase 2, ship the `rtl` filter (1–3 days on top of the core).** Tokenise input with the `vte` crate so SGR colours pass through and stay attached to their graphemes. Default to Persian settings: no line breaking, no padding, folding ي/ك to ی/ک. Offer `--shape none|forms`. This covers `cat`, `git log` with Persian commit messages and `less -R` today, and it serves as the regression harness for everything that follows.

**Phase 3, build the `rtlpty` proxy (the "any app" vehicle).** Use `portable-pty` plus `alacritty_terminal` (its replies to the app come out as `Event::PtyWrite`, so CPR and DSR responses can be answered locally; [docs.rs](https://docs.rs/alacritty_terminal/latest/alacritty_terminal/event/enum.Event.html)) or the wezterm-term and termwiz pair that tattoy uses. `vt100` with its `contents_diff` is enough for an MVP ([docs.rs vt100](https://docs.rs/vt100/latest/vt100/)). Run it inside individual Zellij panes, for example as the pane's default shell wrapper, with WezTerm's BiDi turned off so there's only one owner. It should auto-disable on the alternate screen (parse combined private modes, unlike estaterm's exact-match check) and whenever the child sends `CSI 8 l`. Its targets are Claude Code's streamed output, shell prompts, logs and git: in practice, most of the moments when Persian *content* appears. Editors and lazygit, where most of the *time* goes, stay with app-side support.

**Phase 4, push upstream with the same crate.** In WezTerm, fix the RTL cursor in #784, lam-alef width in #6791, and keep zero-width controls such as ZWNJ and FSI in the model; shaping can only be correct there. In Zellij, help land combining-mark storage (#5500), then open a Discussion proposing per-pane BiDi in core with logical copy. Separately, publish a `ratatui-bidi` adapter that sends `CSI 8 l` plus `CSI 2 SP k` on entry and restores the defaults on exit. ratatui has no RTL work in flight ([ratatui#756](https://github.com/ratatui/ratatui/issues/756)), and its width and diff code was still producing wide-glyph regressions in mid-2026 ([#2685](https://github.com/ratatui/ratatui/issues/2685)), so the adapter needs its own tests.

## Conclusion

The research shifts the question from "which layer fixes RTL?" to "who owns each paragraph, and how do the layers agree on it?". For someone building alone, the valuable piece isn't any one front-end. It's the missing middle layer that every emulator and proxy keeps rebuilding: a conformance-tested, Persian-correct cell-grid layout with cursor and selection maps that speaks BDSM and SCP. Built once in Rust, it turns the filter, the proxy, the ratatui adapter and the WezTerm and Zellij patches into thin consumers rather than five separate attempts at the same problem.

The uncomfortable truth is that in the user's own stack, a proxy will never beat native rendering on shaping or copy. Its value lies in reaching Claude Code and shell output *now*, while upstream moves at its own pace. Two cheap facts settle the remaining design choices: whether WezTerm joins Arabic correctly when it arrives in visual order, and how quickly Zellij merges combining-mark support. Phase 0 exists to measure both before any proxy code is written.
