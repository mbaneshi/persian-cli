> Research notes, compiled 2026-10-11. Scope: theory, standards and expert positions only. Concrete Rust architectures (PTY proxy, emulator plugins, LD_PRELOAD, ratatui) are covered by other researchers. Project prior-art catalog: `/Users/bm/persian-cli/docs/research/prior-art.md`. Facts are dated where they are older than 2025.

## 1. What Egmont Koblinger's "BiDi in Terminal Emulators" recommendation specifies, and who implements it

### Takeaway
The recommendation (v0.1, 2019-01-29, still labelled "draft", with no published revision since) splits responsibility **per paragraph** between two modes. In **implicit** mode, the default, the *terminal* does UAX #9 and shaping on logical-order data, for BiDi-unaware programs like `cat`. In **explicit** mode, which the app selects with `CSI 8 l` (BDSM reset), the *application* does all BiDi and sends visual order. The spec's central claim is that no single layer can do it for every app: only the app knows the whole paragraph, and only the terminal knows the display. As of 2026, VTE is the reference implementation and mintty implements the sequences (marked experimental). WezTerm implements BDSM/SCP behind an opt-in flag, but runs BiDi per line. Konsole, mlterm, PuTTY and Terminal.app do non-conforming, always-on, per-line BiDi. kitty, Alacritty and Ghostty do no BiDi; Ghostty has accepted it in principle.

**Core model**
- **Paragraph = text between hard newlines**, which may span several terminal rows. Terminals already track hard vs. soft wraps for selection, URL detection and rewrap. On the alternate screen, apps conventionally end every line with a hard newline, so paragraphs equal lines there, but "This is just a convention, not a technical necessity." — [Paragraphs](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/paragraphs.html)
- **BiDi is display-only.** Escape sequences and characters operate on the logical "model" (TR/53's "data layer"). BiDi is a "transformation" applied when the display is drawn. The "view" should be defined as model plus transformation, so that selection can map back to logical order. "Cells are always shuffled within a single line", although the shuffle can depend on the whole paragraph. Mouse events reported to apps go through the inverse transformation, so the app gets the model column. — [BiDi is display-only](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/display-only.html)
- **Three per-paragraph flags** (implicit/explicit, autodetect on/off, LTR/RTL) give 6 stored modes and 4 layouts (implicit LTR/RTL, explicit LTR/RTL). — [The basic modes](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/basic-modes.html)
- **Implicit mode**: "doing BiDi and shaping are the sole responsibilities of the terminal emulator", the stream carries logical order, and it is meant for "BiDi-unaware apps, typically simple utilities". It "must be the default" because utilities like `cat` have nowhere to send a mode switch. At level 1, BiDi control characters are discarded. Arabic shaping "is performed on the paragraph, before splitting to lines." — [The basic modes](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/basic-modes.html)
- **Explicit mode**: "doing BiDi is the sole responsibility of the application". The stream carries visual order, and the emulator does no shaping: that too is the app's job, done with presentation-form characters at level 1. It also serves as "damage control" for BiDi-unaware TUIs. Foreign-direction snippets then appear reversed, "but at least the overall UI will remain intact." — [The basic modes](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/basic-modes.html)
- **Autodetection**: UAX #9 doesn't prescribe an algorithm, and first-strong is reasonable. Koblinger discourages using neighbouring paragraphs (the UAX #9 HL1 suggestion) because terminal paragraphs are often unrelated outputs. Empty or all-neutral paragraphs fall back to the stored direction, so there are two autodetect modes, one per fallback. Autodetect is off by default. With autodetection, `cat /etc/services` in RTL mode is "mostly as expected but lone # characters still appear on the wrong side." — [The basic modes](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/basic-modes.html); [The escape sequences](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/escape-sequences.html)
- **Open issue #8**: autodetect once per empty-line-delimited "segment", and around shell prompts using semantic prompt markers. This came from Eli Zaretskii's feedback and is unresolved. — [terminal-wg/bidi issue #8](https://gitlab.freedesktop.org/terminal-wg/bidi/-/issues/8)

**Escape sequences**
- Implicit: `CSI 8 h`; explicit: `CSI 8 l`. This is ECMA-48 **BDSM**, but with the *high* (implicit) state as the default. Apps that want explicit mode switch on startup, set the direction too, and switch back to implicit on exit. — [The escape sequences](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/escape-sequences.html)
- Direction: `CSI 1 SP k` (LTR), `CSI 2 SP k` (RTL), `CSI 0 SP k` / `CSI SP k` (terminal default). This is ECMA-48 **SCP**, with a new value 0, default parameters, and no cursor movement. It applies to both implicit and explicit paragraphs. SCP was chosen over **SPD** (`CSI n SP S`) because SPD sets global properties. Terminals may alias SPD 0/3 to SCP 1/2 for legacy apps. — [The escape sequences](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/escape-sequences.html)
- Temporary DEC private modes: `CSI ? 2500 h/l` mirrors box drawing U+2500–257F in RTL; `CSI ? 2501 h/l` turns autodetection on/off; `CSI ? 1243 h/l` swaps arrow keys (global, default on, only active when the cursor is in an RTL paragraph; Home/End are not swapped). The numbers are "not meant to be final". — [The escape sequences](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/escape-sequences.html); [Arrow keys swapping](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/arrow-key-swapping.html)
- How the modes apply: a BiDi sequence updates the terminal's "current mode". It applies to the current paragraph only if the cursor is at the paragraph's first logical position. New paragraphs created by linefeed inherit the current mode. **ED** (used by ncurses to clear) must turn the cleared lines into one-line paragraphs that carry the current mode. SD/SU and DCH/EL have rules for splitting paragraphs. When a soft wrap joins two paragraphs, the first paragraph's mode wins. — [The escape sequences](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/escape-sequences.html)
- There is no escape sequence for the conformance level. Emulators always use the highest level they implement. — [The escape sequences](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/escape-sequences.html)

**Cursor, erased cells, combining marks, box drawing**
- The terminal's "cursor stands over a character" model "actually comes in handy for BiDi: the cursor can just follow the character it belongs to." The I-beam goes on the right side for RTL-resolved characters. VTE changes the I-beam to ⎡/⎤ to show the direction underneath. With xterm's "about to wrap" state, a cursor that follows its character would jump to mid-line, so VTE lets it walk off-screen. — [The cursed cursor](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/cursor.html)
- Erased cells are mapped to the paragraph-direction end of the line. Trailing erased cells at mid-paragraph line ends are skipped when feeding UAX #9. — [Erased cells](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/erased-cells.html)
- Nonspacing marks stay in their base character's cell in every mode. In explicit mode the app must emit the base followed by its marks even in reversed order. FriBidi does this with `FRIBIDI_FLAG_REORDER_NSM`, but plain UAX #9 output (rule L3) puts marks *before* RTL bases. — [Combining characters](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/combining.html)
- Box drawing (U+2500–257F) and block elements are *not* Bidi_Mirrored, so ncurses borders break in RTL. The spec floats several fixes: patching ncurses, intercepting the calls with **LD_PRELOAD**, or a terminal mode (DECSET 2500) that uses UAX #9 HL6. — [Miscellaneous](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/misc.html)
- Implicit mode needs the **whole paragraph**, including scrollback lines that are off-screen. Emulators can cap paragraphs (for example, render paragraphs over 500 lines as explicit) and keep extra hidden scrollback so that trimming doesn't change the layout. — [Miscellaneous](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/misc.html)
- Pathnames: implicit BiDi can shuffle text across `/`. The proper fix is for utilities to wrap components in isolates, which needs "implicit level 2", where the terminal remembers BiDi controls. Non-standard "stop characters" or color-change breaks are allowed only as non-default settings. — [Miscellaneous](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/misc.html)

**Future levels (not specified)**
- Implicit level 2 would store up to N preceding and succeeding BiDi controls per cell, bit-packed (for example 4+7 in 32 bits), and must support isolates. It might also add escape-sequence forms of BiDi controls and of ZWJ/ZWNJ that are dropped on copy. — [Implicit mode, level 2](https://terminal-wg.pages.freedesktop.org/bidi/future-improvement-ideas/implicit-level2.html)
- Explicit level 2 would add a per-character "logical order" integer sent by the app, so the terminal can copy and search in logical order. Without it, copy and search are broken in explicit mode, and mirrorable characters inside foreign-direction runs must be swapped by the app. — [Explicit mode, level 2](https://terminal-wg.pages.freedesktop.org/bidi/future-improvement-ideas/explicit-level2.html)
- Ecosystem idea: default BiDi-unaware fullscreen apps to explicit mode by adding the BDSM-reset sequence to terminfo `smcup`/`rmcup`, with per-app exceptions through a different `$TERM`. Koblinger rejects making the normal and alternate screens behave differently by default. Simple utilities (`ls`, `grep`) could wrap filenames in FSI…PDI (this needs level 2). Text transformers (`cut`, `sed`) "should not be modified". — [The bigger ecosystem](https://terminal-wg.pages.freedesktop.org/bidi/future-improvement-ideas/ecosystem.html)
- The spec considered and rejected an "emulated explicit mode" that wraps each paragraph in LRO/RLO…PDF. It calls this "a nasty hack": screen libraries can't keep the overrides intact across partial updates, it can't serve as damage control, and the controls end up in copied text. — [Emulated explicit mode](https://terminal-wg.pages.freedesktop.org/bidi/rationale-and-dropped-ideas/emulated-explicit-mode.html)

### Inferences
- The spec is the only design document in this space. It has been stalled since 2019 (v0.1/v0.2, 10 open issues), and only VTE implements it fully. mintty implements it partially, and WezTerm implements a per-line subset behind an opt-in flag. Any "general" solution has to be compatible with BDSM/SCP, at minimum by honouring `CSI 8 l` from BiDi-aware apps and never reordering explicit paragraphs.
- The spec places BiDi for unaware apps in the terminal's *render* stage, not in the byte stream, because only the render stage can keep the model logical (for copy, search and mouse reporting) and know the window width and soft wraps.
- Even WezTerm, the Rust terminal with a 100%-conformant BiDi crate, runs BiDi per line. Per-paragraph resolution, which needs scrollback context and wrap tracking, is the hard part. Implementers keep skipping it.

## 2. Why it is fundamentally ambiguous for a layer outside the application to reorder text

### Takeaway
Reordering needs the whole paragraph in logical order, plus knowledge of how it was cropped and wrapped, which pieces of text are separate UI fields, and whether the app has already reordered it. A TUI that addresses cells absolutely (vim, htop, mc) sends the terminal *fragments* of a layout that was already cropped. A line-oriented tool (`cat`, `ls`) sends whole logical paragraphs. The byte stream alone can't tell these cases apart, and both an external layer and the terminal may try to "own" BiDi. That produces double reordering, or a layout that falls apart.

### Cited findings
- "A terminal emulator is only aware of the part that it displays, and not what's 'outside' or 'underneath'." In an unwrapped 100-character line in an 80-column window, the emulator never sees the other 20 characters. — [Why terminals are special](https://terminal-wg.pages.freedesktop.org/bidi/bidi-intro/why-terminals-are-special.html)
- "Cropping the in-memory string and then applying the BiDi algorithm produces faulty visual layout; cropping needs to be performed on the BiDi algorithm's result. The BiDi algorithm cannot be run on partial data, it must be run on the entire paragraph, and hence can only be run by someone who is aware of the entire paragraph. The only such component is the application." — [Why terminals are special](https://terminal-wg.pages.freedesktop.org/bidi/bidi-intro/why-terminals-are-special.html)
- "The same applies for shaping, too. Shaping depends on the neighbor characters which are not always known by the terminal emulator." — [Why terminals are special](https://terminal-wg.pages.freedesktop.org/bidi/bidi-intro/why-terminals-are-special.html)
- The other side: making `echo`/`cat` query the width, run BiDi, shape, wrap and align is "Clearly not a feasible approach", and would still break on resize. "There isn't a single mode of operation that can cover all use cases." — [Why terminals are special](https://terminal-wg.pages.freedesktop.org/bidi/bidi-intro/why-terminals-are-special.html)
- "Split responsibility is fragile: the two parties have to exactly agree on the details", including the UBA version and the Unicode database. "Ideally at any point in time the entire responsibility should be at one place – either completely at the terminal, or completely at the app." — [Why terminals are special](https://terminal-wg.pages.freedesktop.org/bidi/bidi-intro/why-terminals-are-special.html)
- TUIs flatten UI layout and text into one text layer. Adjacent UI elements are often separated only by attributes, for example htop or mc's `9PullDn10Quit` as one "word", "so the problem with any approach relying solely on the resolved embedding levels … is a real issue." — [Why terminals are special](https://terminal-wg.pages.freedesktop.org/bidi/bidi-intro/why-terminals-are-special.html)
- Terminals are a "legacy story of 50+ years, with additional layers (screen handling libraries etc.) … none of which had BiDi or shaping in mind". Any fix has to be backward compatible. — [Why terminals are special](https://terminal-wg.pages.freedesktop.org/bidi/bidi-intro/why-terminals-are-special.html)
- On the alternate screen, paragraphs equal lines only by convention. Even then, a full-screen app with a sidebar, or a tmux split, places unrelated text on one row, and a terminal-side UBA would treat it as one paragraph. Koblinger's issue #7 notes that shaping "can't count for the neighboring character if it's outside of the terminal's area designated for displaying that particular word (… a sidebar of the application or a vertical tmux split etc.)". — [Paragraphs](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/paragraphs.html); [terminal-wg/bidi #7](https://gitlab.freedesktop.org/terminal-wg/bidi/-/issues/7)
- Per-line BiDi with autodetection breaks wrapped text. When a foreign word crosses a line boundary, "the entire next line is laid out in opposite base direction". — [Prior work: terminals](https://terminal-wg.pages.freedesktop.org/bidi/prior-work/terminals.html)
- Implicit mode can break BiDi-unaware fullscreen apps that are handed BiDi data. This is why explicit mode doubles as "damage control", and why the spec suggests terminfo `smcup` tricks. — [The bigger ecosystem](https://terminal-wg.pages.freedesktop.org/bidi/future-improvement-ideas/ecosystem.html)
- Cursor and input: in implicit mode, cursor movement is always *logical*. Visual cursor walking in mixed text is impossible without the app. Arrow-key swapping cannot be detected by an app that paints mixed-direction paragraphs: "There's no way the app could reliably tell when exactly the user pressed the key." — [Arrow keys swapping](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/arrow-key-swapping.html)
- Explicit mode (visual order in the stream) breaks terminal-side copy and search: "text fragments of foreign direction will be reversed, searching won't work in Arabic and copy-pasting will result in undesired shaped characters". Fixing that needs inverse BiDi and inverse shaping, and it is "unclear … if there's an 'inverse shaping' algorithm". — [Explicit mode, level 2](https://terminal-wg.pages.freedesktop.org/bidi/future-improvement-ideas/explicit-level2.html); [RTL and BiDi text](https://terminal-wg.pages.freedesktop.org/bidi/bidi-intro/rtl-bidi-text.html)
- Emacs/Koblinger exchange (Feb 2019): Koblinger argued that BiDi must be switched by escape sequences, not by user settings, saying that telling users to turn off BiDi in the emulator's settings is "a user experience no-go". He asked Emacs to emit BDSM. Eli Zaretskii (Emacs maintainer) replied that `bidi-display-reordering nil` already gives LTR "explicit mode", and that "you can hardly expect Emacs (or any other application) to support control sequences that are not yet defined, let alone standardized." — [Unicode ML 2019-02 thread](https://unicode.org/mail-arch/unicode-ml/y2019-m02/0139.html); [search summary of thread](https://www.unicode.org/mail-arch/unicode-ml/y2019-m01/0350.html)
- Neovim #553 "Bidi language support" has been open since 2014-04-17 (verified 2026-10-08). — `/Users/bm/persian-cli/docs/research/prior-art.md`, citing [neovim#553](https://github.com/neovim/neovim/issues/553)
- Project prior art: every stream transformer (estaterm, fa-console, ar-terminal path B) writes visual order and presentation forms into the stream, breaks copy, search and ANSI sequences, and gives up on full-screen apps (estaterm skips the alternate screen). None of the terminal-side implementations negotiate ownership through BDSM. — `/Users/bm/persian-cli/docs/research/prior-art.md`
- kitty's documentation explicitly recommends combining `force_ltr` with external FriBidi. This is the one mainstream acknowledgment of an external visual-order layer, and it comes with kitty's own caveat that selection gives the wrong character. — [kitty definition.py](https://raw.githubusercontent.com/kovidgoyal/kitty/master/kitty/options/definition.py)

### Inferences
- A layer between app and terminal, such as a PTY proxy, sees only the byte stream: characters plus cursor-addressing sequences. For line-oriented output it can rebuild paragraphs, but then it is either (a) emitting visual order, which is explicit mode with all its copy, search and shaping costs, or (b) duplicating what an implicit-mode terminal does better at render time. For absolutely-addressed TUIs it gets cells from an already-cropped layout. Reordering those is exactly the "crop then BiDi" error Koblinger identifies. To be correct it would need to keep a full virtual screen (essentially a terminal emulator) and still guess paragraph and field boundaries.
- Double ownership is a real risk. If the proxy emits visual order and the outer terminal does implicit BiDi (VTE by default, Konsole, mintty, WezTerm with `bidi_enabled`), the text is reordered twice. A correct layer would have to emit `CSI 8 l` (explicit) for the outer terminal. That only works on terminals that honour BDSM, and it gives up the terminal's logical copy.
- The "fully general" fix is therefore unsound in theory. The best available is a heuristic policy: implicit-style help for line-oriented output on the primary screen, and hands-off (or explicit-mode damage control) on the alternate screen or when the app signals BiDi awareness. That is what estaterm and mintty's `Bidi=1` approximate.

### Gaps
- I found no formal impossibility proof beyond Koblinger's argument; this is reasoned position, not theorem.
- I found no published measurement of how often real TUIs end alternate-screen lines with hard newlines versus cursor addressing. This affects how well a proxy can infer paragraphs.

## 3. Arabic/Persian shaping in a fixed-cell grid

### Takeaway
Arabic-script letters join cursively. Most letters have 4 contextual forms and right-joining letters have 2. ZWNJ (U+200C), which Persian needs constantly (plural ـها, prefix می‌), breaks joining without taking width. The lam-alef ligature is obligatory and turns 2 code points into 1 glyph, which conflicts with 2 cells. Harakat are nonspacing marks of width 0. Presentation forms (U+FB50–FDFF, FE70–FEFF) are compatibility characters that "should not be used in general interchange". Experts favour HarfBuzz shaping at render time, but most terminals that shape (VTE, estaterm and others) still use FriBidi presentation forms, because forms map 1:1 to cells.

### Cited findings
- "Dual-joining characters have four distinct forms, for isolated, final, medial, and initial contexts"; "Right-joining characters have only two distinct forms". Transparent characters (nonspacing marks, most format controls) "do not affect the joining behavior". — [Unicode 18.0 Core Spec ch. 9, §9.2.1/§9.2.3](https://www.unicode.org/versions/Unicode18.0.0/core-spec/chapter-9/)
- ZWNJ "prevents those letters from forming a cursive connection"; "Examples requiring the use of a non-joiner include the Persian plural suffix". ZWJ "permits that letter to form a cursive connection without a visible neighbor". — [Unicode Core Spec ch. 9, §9.2](https://www.unicode.org/versions/Unicode18.0.0/core-spec/chapter-9/)
- "When supported by the style of the font, lam-alef ligatures are considered obligatory." — [Unicode Core Spec ch. 9, §9.2.2](https://www.unicode.org/versions/Unicode18.0.0/core-spec/chapter-9/)
- Presentation forms "should not be used in general interchange" and are "encoded as characters primarily for compatibility reasons". — [Unicode Core Spec ch. 9, §9.2.2, §9.2.10](https://www.unicode.org/versions/Unicode18.0.0/core-spec/chapter-9/)
- Harakat are "the subset of tashkil which denote short vowels", written as combining marks. — [Unicode Core Spec ch. 9, §9.2](https://www.unicode.org/versions/Unicode18.0.0/core-spec/chapter-9/)
- UCD properties (checked locally with Python `unicodedata`, UCD 15.0): ZWNJ U+200C and ZWJ U+200D are category Cf with bidi class **BN**. FATHA U+064E and superscript alef U+0670 are Mn/**NSM**. U+FEFB (lam-alef isolated ligature) is a single AL code point whose NFKC decomposition is `U+0644 U+0627`, two characters. TATWEEL U+0640 is AL/Lm. FARSI YEH U+06CC and PEH U+067E are AL. — [Unicode Character Database / DerivedBidiClass.txt](https://www.unicode.org/Public/UCD/latest/ucd/extracted/DerivedBidiClass.txt) (values verified with Python's `unicodedata`)
- Koblinger's intro describes two shaping approaches. The older one replaces code points with presentation forms (FriBidi has such methods), and "allegedly … cannot perfectly render every possible text of every related language". "The preferred method is to avoid the presentation form characters, and use a library (e.g. HarfBuzz)." It cites CSS3: wrapped Arabic "must still be shaped … as if the word were still whole", and he applies this to cropped text too. — [RTL and BiDi text](https://terminal-wg.pages.freedesktop.org/bidi/bidi-intro/rtl-bidi-text.html)
- Spec issue #7, "Rework shaping" (2019), after feedback on the Unicode list: "Shaping shouldn't be done using presentation form characters (in explicit mode)… Shaping needs to be done by the emulator, on the characters it displays, even in explicit mode." Joining across invisible neighbours (a sidebar or tmux split) might later need per-cell "imaginary left/right neighbors", or ZWNJ break points. This contradicts the published level-1 text, which puts explicit-mode shaping in the app; the issue is still open. — [terminal-wg/bidi #7](https://gitlab.freedesktop.org/terminal-wg/bidi/-/issues/7); [The basic modes](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/basic-modes.html)
- Spec issue #4, "Arabic joining", opened by the mintty author: lam-alef joining is "a strict requirement". mlterm appends the following text right after the ligature, while mintty "leaves a space after it", which is "consistent with the character-based locale-related width properties, which I think a terminal should maintain". He asks for a statement or a switchable mode. — [terminal-wg/bidi #4](https://gitlab.freedesktop.org/terminal-wg/bidi/-/issues/4)
- mintty's resolution: `CSI ? 2521 l` (default) gives a two-cell lam-alef, `CSI ? 2521 h` a single cell. — [mintty CtrlSeqs](https://github.com/mintty/mintty/wiki/CtrlSeqs)
- VTE disables lam-alef ligatures entirely ("Don't do Arabic ligatures as per bug 142"). It shapes with FriBidi presentation forms, does not shape across soft wraps, and says this "should be replaced by HarfBuzz". — [VTE src/bidi.cc](https://raw.githubusercontent.com/GNOME/vte/master/src/bidi.cc)
- A 2019 Unicode-list post asks: "Lam-alif would be trickier - one cell or two?" — [Unicode ML 2019-01/0404](https://www.unicode.org/mail-arch/unicode-ml/y2019-m01/0404.html)
- Python `wcwidth` documents that "no established formal standards exist at present on which Unicode character shall occupy how many cell positions on character terminals." — [wcwidth source docs](https://wcwidth.readthedocs.io/en/latest/_modules/wcwidth/_wcwidth.html)
- A real-world width bug: Arabic with diacritics rendered "with gap between every letter" because a width function (Bun.stringWidth) gave combining marks width 1. This comes from an aggregator copy of a Claude Code issue. — [claudeissues.com #60701](https://claudeissues.com/issue/60701-arabic-with-diacritics-renders-with-gap-between-every-letter-bun-stringwidth-tre)
- In explicit mode, combining marks must follow their base even when the text is reversed. Plain UAX #9 output (rule L3) puts marks before RTL bases, so apps must fix the order. — [Combining characters](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/combining.html); [UAX #9 L3](https://www.unicode.org/reports/tr9/)
- UAX #9 §3.5.1: where shaping is involved, "the width calculations must be based on the shaped glyphs." — [UAX #9](https://www.unicode.org/reports/tr9/)
- Project finding: Layer 3 (width) "is unsolved everywhere". Projects squash, clip or overflow shaped glyphs. — `/Users/bm/persian-cli/docs/research/prior-art.md`
- Ghostty's discussion lists the same problems: letters disconnected without joining, careful segmentation of marks and digits, and logical columns not matching visual positions on RTL rows. — [ghostty discussion #9774](https://github.com/ghostty-org/ghostty/discussions/9774)

### Inferences
- The cell grid relies on the app, the terminal and any middle layer all agreeing on `wcwidth`. Presentation forms keep 1 code point per cell (except lam-alef), which is why stream transformers like them. HarfBuzz output (advance widths, ligatures, mark positioning) doesn't fit the grid. Rendering it means drawing shaped runs over N cells and squashing or padding them, which only a renderer can do.
- Lam-alef forces a choice with no clean answer. Two cells with a padding gap (mintty default, locale-consistent) keep cursor arithmetic correct. One cell (mlterm, mintty 2521h) looks right but disagrees with every app's width count. Disabling the ligature (VTE) is typographically wrong.
- ZWNJ is BN and zero-width. A layer that drops zero-width characters (as WezTerm does for some) or a width table that gives it width 1 will break Persian words. Persian support must keep ZWNJ in the cell (attached like a combining mark) and treat it as a joining break in shaping.
- A middle layer that emits presentation forms permanently corrupts the data: copy yields FBxx/FExx code points and search fails. This conflicts with the project's logical-buffer principle. A terminal-side renderer can shape without changing stored code points.

### Gaps
- I could not reach "bug 142" in VTE (which tracker?) to read the reasoning for disabling lam-alef.
- I found no authoritative spec for the cell width of a lam-alef ligature, or for ZWNJ in terminals. wcwidth implementations give it 0, but terminals differ, and I did not survey them.
- I did not examine Unicode's newer terminal-oriented width work (if any) for 2025–2026.

## 4. UAX #9 specifics that matter for terminals

### Takeaway
UAX #9 (Unicode 18.0, revision 52, 2026-09-01) resolves levels per *paragraph* but reorders per *line* (rules L1–L4, after wrapping). That fits the terminal model "paragraph = hard-newline segment, shuffle within rows". Several rules bite in a grid. L1 sends trailing whitespace to the paragraph-direction end of the line. Paired brackets (BD16/N0) need a 63-deep stack across the paragraph. L4 mirroring applies only to Bidi_Mirrored characters, which excludes box drawing. Persian digits (U+06F0–06F9) are **EN** while Arabic-Indic digits (U+0660–0669) are **AN**, and W2 turns EN into AN after an AL character. Neutrals at line edges take the paragraph direction, which is why `#`, bullets and punctuation land on the "wrong" side in autodetected terminal output.

### Cited findings
- Version: UAX #9 for Unicode 18.0.0, revision 52, dated 2026-09-01. — [UAX #9](https://www.unicode.org/reports/tr9/)
- §3.4: rules L1–L4 "act on a per-line basis and are applied **after** any line wrapping is applied to the paragraph". The paragraph level is set earlier (P2/P3). — [UAX #9](https://www.unicode.org/reports/tr9/)
- L1: "reset the embedding level of the following characters to the paragraph embedding level". This covers segment and paragraph separators, plus whitespace and isolate formatting characters at the end of a line, so trailing whitespace appears at the visual end of the line in the paragraph direction. — [UAX #9](https://www.unicode.org/reports/tr9/)
- The spec relies on L1: "the BiDi algorithm places trailing logical whitespaces to the trailing side", so erased cells and spaces look the same after shuffling. — [Erased cells](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/erased-cells.html)
- P2/P3: the paragraph level comes from "the first character of type L, AL, or R", skipping isolate content, and is 0 if none is found. HL1: "Override P3, and set the paragraph embedding level explicitly". This is what SCP maps to. — [UAX #9](https://www.unicode.org/reports/tr9/)
- Other higher-level protocols: HL2 "Override W2, and set EN or AN explicitly"; HL3 "Emulate explicit directional formatting characters"; HL4 "Apply the Bidirectional Algorithm to segments"; HL6 allows mirrored glyphs for non-Bidi_Mirrored characters "in specialized contexts" (the spec's basis for box mirroring). — [UAX #9](https://www.unicode.org/reports/tr9/); [Miscellaneous](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/misc.html)
- BD16 uses a bracket-pair stack of "exactly 63 elements". N0 gives both brackets of a pair the embedding direction when a matching strong type is inside. — [UAX #9](https://www.unicode.org/reports/tr9/)
- L4: a character is mirrored when "the resolved directionality of that character is R" and its Bidi_Mirrored property is Yes. `(` U+0028 is Bidi_Mirrored = Yes (verified with Python `unicodedata.mirrored`). — [UAX #9](https://www.unicode.org/reports/tr9/)
- Digits: Table 4 lists EN as "European digits, Eastern Arabic-Indic digits, …" and AN as "Arabic-Indic digits, Arabic decimal and thousands separators". W2: "If an AL is found, change the type of the European number to Arabic number." UCD check: U+06F4 EXTENDED ARABIC-INDIC DIGIT FOUR = EN; U+0664 ARABIC-INDIC DIGIT FOUR = AN; U+066B/066C Arabic decimal/thousands separators = AN; U+060C ARABIC COMMA = CS. — [UAX #9](https://www.unicode.org/reports/tr9/); [Unicode Core Spec ch. 9 (Persian, Sindhi, Urdu use the Eastern Arabic-Indic digit sequence)](https://www.unicode.org/versions/Unicode18.0.0/core-spec/chapter-9/)
- Isolates (LRI, RLI, FSI, PDI) have "the effect of a neutral" on surrounding text. Koblinger: any emulator claiming implicit level 2 must support isolates. "5+ years after their debut there's no excuse." — [UAX #9](https://www.unicode.org/reports/tr9/); [Implicit mode, level 2](https://terminal-wg.pages.freedesktop.org/bidi/future-improvement-ideas/implicit-level2.html)
- Terminals at level 1 (VTE, Konsole, PuTTY per the 2019 tests) and WezTerm (zero-width elision) **discard** BiDi control characters. So LRI…PDI or ALM (U+061C) emitted by apps have no effect, and the controls are lost on copy. — [The basic modes](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/basic-modes.html); [Prior work: terminals](https://terminal-wg.pages.freedesktop.org/bidi/prior-work/terminals.html); [WezTerm performer.rs](https://raw.githubusercontent.com/wezterm/wezterm/main/term/src/terminalstate/performer.rs)
- Neutrals at edges: `echo '12345 HEBREW'` in PuTTY reversed the number and misaligned it, and `cat /etc/services` with autodetection leaves lone `#` on the wrong side. A Konsole 24.x report: a neutral bullet at line start makes the direction LTR. — [Prior work: terminals](https://terminal-wg.pages.freedesktop.org/bidi/prior-work/terminals.html); [The escape sequences](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/escape-sequences.html); [claudeissues.com #51146](https://claudeissues.com/issue/51146-bidi-hardcoded-assistant-message-bullet-breaks-rtl-rendering-for-hebrew-arabic-p)

### Inferences
- Persian digits being EN while Arabic-Indic digits are AN means mixed Persian text with numbers resolves differently from Arabic text. W2 turns EN after AL into AN, so the Persian case usually converges, but an implementation must use the real UCD classes and not "Arabic script = RTL" heuristics. Ghostty maintainers made the same point when they rejected hand-rolled script detection.
- Terminal-specific paragraph policy (per row, per hard-newline paragraph, or per segment as in issue #8) sits *outside* UAX #9, which leaves it to higher-level protocols. A layer that defines paragraphs differently from the outer terminal will produce different layouts, the split-responsibility problem from section 2.
- Because level-1 terminals strip BiDi controls, the cheapest app-side fix (wrap paths and code in LRI…PDI, as the `rtl-terminal` prior art suggests) only works on level-2 terminals, and none exist.

### Gaps
- I did not read the remaining ~34k characters of UAX #9 (HL5, HL6 text, section 5+). HL6 is quoted from the terminal-wg spec, not directly from UAX #9.
- Python's local UCD is 15.0. I did not recheck bidi classes against UCD 18.0, though digit and ZWNJ classes have been stable for many versions.

## 5. What experts say about where BiDi should live

### Takeaway
The experts agree there is no single home. Koblinger (author of the spec and the VTE implementation): the *terminal* does BiDi and shaping for unaware apps (implicit, the default), the *application* does it when it knows more (explicit, which it must request by escape sequence), and responsibility should never be split for the same paragraph. Zaretskii (Emacs): the application already does full BiDi and won't adopt unstandardized sequences. Unicode-list feedback (Richard Wordingham, per issue #7): shaping belongs in the emulator even in explicit mode, not in presentation forms. Hashimoto (Ghostty): full BiDi is a very large effort, only single-line, renderer-level RTL is planned. kitty (Goyal): no BiDi, use `force_ltr` plus external FriBidi.

### Cited findings
- Koblinger: "Ideally at any point in time the entire responsibility should be at one place – either completely at the terminal, or completely at the app." — [Why terminals are special](https://terminal-wg.pages.freedesktop.org/bidi/bidi-intro/why-terminals-are-special.html)
- Koblinger: implicit is the default because simple utilities can't send mode switches. BiDi-aware apps should switch to explicit mode themselves and not rely on "magic" such as terminfo. — [The basic modes](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/basic-modes.html); [The bigger ecosystem](https://terminal-wg.pages.freedesktop.org/bidi/future-improvement-ideas/ecosystem.html)
- Koblinger confirms "ECMA TR/53's realization of 28 years ago, there have to be two substantially different modes", and that the switch must come from escape sequences, not user settings. — [Unicode ML 2019-02](https://unicode.org/mail-arch/unicode-ml/y2019-m02/0139.html)
- Koblinger on TR/53: the risk of "a standard that no one implements for decades (as it happened to ECMA TR/53)". He rejected TR/53's SIMD/SDS/SRS for logical-order reconstruction. — [Why terminals are special](https://terminal-wg.pages.freedesktop.org/bidi/bidi-intro/why-terminals-are-special.html); [Explicit mode, level 2](https://terminal-wg.pages.freedesktop.org/bidi/future-improvement-ideas/explicit-level2.html)
- Koblinger on explicit-mode apps: "The cleanest solution is to encourage all the responsibility being at one place, and that one place is the application in case of explicit mode. Just as such applications provide their own search functionality, probably they should handle mouse selection and copy-paste themselves too." — [Explicit mode, level 2](https://terminal-wg.pages.freedesktop.org/bidi/future-improvement-ideas/explicit-level2.html)
- Koblinger (2019) considered LD_PRELOAD interception of ncurses border calls as one option for RTL box drawing, alongside fixing ncurses or a terminal mode. — [Miscellaneous](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/misc.html)
- Eli Zaretskii: `bidi-display-reordering nil` already gives (LTR-only) explicit mode. "You can hardly expect Emacs (or any other application) to support control sequences that are not yet defined, let alone standardized. When they become sufficiently widely available, I'm sure someone will add them to Emacs." — [Unicode ML 2019-02 thread](https://unicode.org/mail-arch/unicode-ml/y2019-m02/0139.html)
- Eli's feedback also led to issue #8 (autodetect direction per empty-line-delimited segment, as Emacs does). — [terminal-wg/bidi #8](https://gitlab.freedesktop.org/terminal-wg/bidi/-/issues/8)
- Richard's feedback on the Unicode list, via issue #7: shaping must be done by the emulator, not with presentation forms. — [terminal-wg/bidi #7](https://gitlab.freedesktop.org/terminal-wg/bidi/-/issues/7)
- mintty author (issue #4): a terminal should keep "character-based locale-related width properties", so lam-alef stays two cells by default. — [terminal-wg/bidi #4](https://gitlab.freedesktop.org/terminal-wg/bidi/-/issues/4)
- PuTTY's own semi-bug page (as quoted in the spec, 2019): "Proper support for this will need to involve a properly thought out design". — [Prior work: terminals](https://terminal-wg.pages.freedesktop.org/bidi/prior-work/terminals.html)
- Mitchell Hashimoto (Ghostty, 2024-02-02): full BiDi "requires a very significant amount of effort". He had read the terminal-wg spec and is "not ready" to implement it, but keeps a renderer/shaping-only single-line RTL issue open: "One day, I'd like to support this." — [ghostty #1442](https://github.com/ghostty-org/ghostty/issues/1442)
- Ghostty maintainers (2025–2026) gate RTL on LTR-performance benchmarks and small PRs, and say full support "requires a much larger scope" than shaper fixes. — [ghostty discussion #9774](https://github.com/ghostty-org/ghostty/discussions/9774)
- kitty: no BiDi. The documented path is `force_ltr` plus external GNU FriBidi, which "expects [LTR] for terminals". — [kitty definition.py](https://raw.githubusercontent.com/kovidgoyal/kitty/master/kitty/options/definition.py)
- An Xfce Terminal RTL request was closed WONTFIX. One commenter wrote that if BiDi in terminals were simple, the VTE developers would have done it long ago (via search snippet; I didn't open the page). — [Xfce bug 12576](https://bugzilla.xfce.org/show_bug.cgi?id=12576)

### Inferences
- The expert position rules out an external "universal" layer as the *owner* of BiDi. The sanctioned architecture is terminal-side implicit BiDi (rendering, logical model) plus app-side explicit BiDi, coordinated by BDSM/SCP. A helper that lives outside both can at most act like a terminal (a full emulator or multiplexer that renders), or like an app (rewriting the output of specific known programs). It can't do both transparently for unknown programs.
- A multiplexer-style helper (a terminal inside a terminal, like tmux or Zellij) is the one place outside the app that does have the full grid, scrollback and pane boundaries. That makes it the closest thing to "terminal-side" an add-on can be. It still has to send the outer terminal visual order (explicit mode), with the copy and search costs that brings. This is an inference; no source evaluates it.
- Nobody has solved Persian input/IME and ZWNJ entry at the terminal level. The spec covers only arrow-key swapping.

- I did not locate the mlterm author's (Araki Ken) position on where BiDi should live.
- I found no statements from Alacritty or kitty maintainers beyond documentation text.
